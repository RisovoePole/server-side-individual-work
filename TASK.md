
Индивидуальная работа
Разработка server-side приложения на Node.js по полученной теме
Все требования документа являются обязательными
Цель работы
Самостоятельно разработать полноценное server-side приложение по теме, полученной во время
жеребьёвки, применив Node.js, Express.js, архитектуру MVC, PostgreSQL, Sequelize, EJS,
аутентификацию, авторизацию, валидацию, обработку ошибок и обмен данными в реальном
времени.
1 Тема и самостоятельность выполнения
Каждый студент выполняет проект по теме, указанной в вытянутой им бумажке. Тема уже
закреплена за студентом. Обмен темами или изменение темы допускается только с разрешения
преподавателя.
Студент самостоятельно анализирует предметную область, определяет модели, их поля, связи,
маршруты, функции приложения и права пользователей. Проект не должен повторять учебное
приложение из лабораторных работ без адаптации к полученной теме.
К защите представляется собственный проект. Студент должен понимать весь представленный код
и уметь изменить его во время защиты.
2 Проектирование приложения
До начала программирования подготовьте краткое описание проекта, включающее:
• полученную тему и название приложения;
• назначение приложения и его основных пользователей;
• перечень моделей и основных полей;
• связь между моделями;
• основные маршруты;
• возможности обычного пользователя;
• возможности администратора.
Описание включается в файл README.md и используется при защите.

5 База данных и модели
Создайте отдельную базу данных PostgreSQL. Параметры подключения храните в файле .env.
Пароль базы данных, секрет сессии и другие конфиденциальные значения запрещается записывать
непосредственно в исходном коде.
DB_HOST=localhost
DB_PORT=5432
DB_NAME=project_database
DB_USER=postgres
DB_PASSWORD=your_password
SESSION_SECRET=your_secret
PORT=3000
Проект должен содержать минимум три модели:
1. User - пользователь приложения.
2. Первая модель предметной области.
3. Вторая модель предметной области.
Между двумя моделями предметной области установите связь One-to-Many. Каждая модель
предметной области должна содержать минимум четыре информативных поля, не считая id,
createdAt и updatedAt.

6 Модель пользователя
Поле Требование
id Primary key, auto increment
name Обязательное имя пользователя
email Обязательное и уникальное значение
password Пароль только в виде hash
role Значение user или admin
lastLogin Дата и время последнего успешного входа
Новый пользователь автоматически получает роль user. Возможность выбрать роль admin в
регистрационной форме запрещена.
7 Операции с данными
Для обеих моделей предметной области реализуйте полный набор операций CRUD:
Операция Требование
Create Форма добавления и сохранение записи в PostgreSQL
Read Список записей и отдельная страница одной записи
Update Форма с текущими значениями и сохранение изменений
Delete Удаление после подтверждения пользователя
Связанный объект выбирается из выпадающего списка. Пользователь не должен вручную вводить
foreign key. На странице родительской записи отобразите связанные записи, а на странице
дочерней записи - информацию о родительском объекте.
8 Регистрация и вход
8.1 Регистрация
Реализуйте маршруты GET /register и POST /register. Форма содержит имя, email, пароль и
подтверждение пароля. Проверьте заполнение полей, формат и уникальность email, минимальную
длину пароля шесть символов и совпадение паролей. Перед сохранением обработайте пароль с
помощью bcrypt.
8.2 Вход и выход
Реализуйте GET /login, POST /login и POST /logout. При входе найдите пользователя по email,
сравните пароль через bcrypt, создайте сессию и обновите lastLogin. При выходе сессия должна
быть удалена. Пароль или его hash запрещается сохранять в сессии.
8.3 Профиль
Защищённая страница GET /profile отображает имя, email, роль, дату регистрации и последний
успешный вход. Пароль и его hash на странице не отображаются.

9 Авторизация и роли
Создайте middleware isAuthenticated и isAdmin. Защита должна выполняться на сервере, а не только
путём скрытия кнопок в EJS.
Действие Гость User Admin
Просмотр общедоступных данных Да Да Да
Поиск, фильтрация и сортировка Да Да Да
Просмотр профиля Нет Да Да
Просмотр статистики Нет Да Да
Добавление данных Нет Нет Да
Редактирование данных Нет Нет Да
Удаление данных Нет Нет Да
Если предметная область предполагает другие действия обычного пользователя, их можно
добавить, но административные функции должны оставаться защищёнными.
10 Поиск, фильтрация и сортировка
Для основной модели реализуйте:
• поиск минимум по одному текстовому полю без учёта регистра;
• минимум два фильтра, соответствующих полученной теме;
• сортировку минимум по одному полю в двух направлениях;
• одновременную работу поиска, фильтров и сортировки.
Условия должны применяться на уровне Sequelize. Не следует сначала загружать все записи, а
затем фильтровать их в JavaScript.
11 Валидация
Используйте express-validator. Проверяйте обязательные поля, формат email, числа и допустимые
диапазоны, длину строк, параметры ID, уникальные значения и существование связанной записи.
Некорректные данные не должны сохраняться в базе.
Пользователь должен получать понятные сообщения. При повторном показе формы ранее
введённые безопасные данные должны сохраняться; пароль повторно не отображается.
Страница 5
12 Обработка ошибок
Создайте middleware notFound и errorHandler, а также страницы 403.ejs, 404.ejs и error.ejs.
Код Ситуация
400 Некорректные входные данные
401 Пользователь не выполнил вход
403 Недостаточно прав
404 Маршрут или запись не найдены
409 Конфликт уникальных данных
500 Внутренняя ошибка сервера
Все асинхронные операции выполняйте через async/await с передачей ошибок в центральный
обработчик. Пользователю запрещается показывать stack trace, пароль, содержимое .env или
технические детали SQL-запросов.
13 Логирование
Подключите Morgan. Логи выводятся в терминал и сохраняются в файл. Каждая запись должна
содержать HTTP-метод, URL, status code и время выполнения запроса.
GET /items | 200 | 12 ms
POST /login | 302 | 25 ms
POST /items | 403 | 4 ms
14 Статистика
Создайте защищённую страницу GET /statistics. Она должна отображать минимум четыре
показателя, соответствующих полученной теме: общее количество записей, распределение по
категории или статусу, агрегированное значение и запись с максимальным или минимальным
показателем. Статистика рассчитывается на основании данных PostgreSQL.
15 Уведомления в реальном времени
Используйте Socket.IO. Когда администратор добавляет новую запись основной модели, все
подключённые пользователи должны получить уведомление без перезагрузки страницы.
Уведомление содержит название объекта, имя администратора, дату и время и автоматически
исчезает либо закрывается пользователем.
Работу функции необходимо проверить одновременно в двух окнах браузера.
