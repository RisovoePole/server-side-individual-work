## 1. Почему я выбрал такую тему и что получилось

Мне досталась тема «Система бронирования спортивных площадок». Я сделал полноценное
server-side приложение: публичный каталог площадок, расписание броней, регистрацию и вход
пользователей, разделение прав, поиск с фильтрами и сортировкой, валидацию, статистику,
логирование и уведомления в реальном времени.

Идея простая: тренер или обычный человек заходит на сайт, смотрит, какие площадки есть
в городе, читает описание и цену, видит занятое время и бронирует площадку на нужный час.
Администратор управляет каталогом: добавляет, редактирует и удаляет площадки и брони.
Когда администратор добавляет новую площадку, все открытые вкладки пользователей сразу
получают уведомление — перезагружать страницу не нужно.

## 2. Назначение и пользователи

- **Гость** видит каталог и расписание, может искать и фильтровать площадки, но не может
  бронировать и просматривать защищённые страницы.
- **Зарегистрированный пользователь (role = `user`)** может забронировать площадку,
  отменить **только свою** бронь, смотреть профиль и статистику.
- **Администратор (role = `admin`)** делает всё то же самое и дополнительно управляет
  площадками и всеми бронями: создание, редактирование, удаление, смена статуса брони.

В регистрационной форме нет поля «роль» — новый пользователь всегда получает `user`.

## 4. Проектирование: модели и связи

### User — пользователь

| Поле | Описание |
| --- | --- |
| `id` | первичный ключ, автоинкремент |
| `name` | имя, обязательное, 2–50 символов |
| `email` | обязательный, уникальный, нормализуется и проверяется как email |
| `password` | только bcrypt-хэш (60 символов, префикс `$2b$`) |
| `role` | `user` или `admin`, по умолчанию `user` |
| `lastLogin` | дата и время последнего успешного входа |
| `createdAt`, `updatedAt` | служебные поля Sequelize |

### Venue — спортивная площадка (основная модель предметной области)

`title`, `sport`, `address`, `city`, `pricePerHour`, `description`, `photoUrl` —
7 информативных полей, не считая `id` и служебных полей. Вид спорта выбирается из списка:
футбол, теннис, баскетбол, волейбол, фитнес, бадминтон.

### Booking — бронь площадки (дочерняя модель)

`date`, `startTime`, `endTime`, `status`, `comment` — 5 информативных полей.
Статус бывает `confirmed` (подтверждена) или `cancelled` (отменена). Отменённая бронь
остаётся в базе и видна в расписании, но время площадки она уже не блокирует.

### Связи

```
Venue (1) ────< (many) Booking      // основная связь One-to-Many задания
User  (1) ────< (many) Booking      // помним, кто забронировал площадку
```

`Booking.venueId` и `Booking.userId` — внешние ключи с `ON DELETE CASCADE`: при удалении
площадки или пользователя его брони удаляются автоматически. Пользователь никогда не
вводит foreign key руками: площадка выбирается из `<select>`, а `userId` берётся из сессии.

## 7. Как устроена работа приложения

**MVC и жизненный цикл запроса.** Express последовательно проходит через Morgan, статику, разбор формы,
сессию, middleware с общими переменными для EJS (`currentUser`, `flash`, справочники),
затем запрос попадает в нужный `routes/*`. Маршрут только задаёт URL и цепочку middleware;
контроллер вызывает Sequelize и рендерит шаблон. Модели описывают таблицы и связи.
Ошибки из `async/await` подхватываются `asyncHandler` и уходят в `errorHandler`.

**Регистрация и вход.** `express-validator` проверяет имя, формат и уникальность email,
минимальную длину пароля (6) и совпадение с подтверждением. Перед `User.create()` пароль
проходит через `bcrypt.hash(..., 12)`. При входе пользователь ищется по email, пароль
сравнивается через `bcrypt.compare()`, после успешного входа обновляется `lastLogin`.
В сессию кладутся только `id`, `name`, `email`, `role` — ни пароля, ни хэша там нет.
Сессии хранятся в таблице `Sessions` в PostgreSQL, поэтому перезапуск контейнера не
разлогинивает пользователя.

**Поиск, фильтры и сортировка.** В `venueController.index` я строю `where` для Sequelize:
`Op.iLike` по названию и адресу (регистр не важен), точный фильтр по виду спорта,
`Op.iLike` по городу, `order` по одному из трёх полей в двух направлениях. Всё это работает
одновременно и выполняется SQL-запросом, а не перебором массива в JavaScript.

**Валидация.** Проверяются обязательные поля, email, числа и диапазоны цены/суммы, длина
строк, формат даты `ГГГГ-ММ-ДД` и времени `ЧЧ:ММ`, порядок времени, реальность выбранной
площадки (`venueId` ищется в БД), корректность `id` в URL и уникальность email. При ошибке
форма показывается снова со статусом 400 и ранее введёнными безопасными значениями;
поля пароля всегда пустые.

**Обработка ошибок.** Есть `notFound` и `errorHandler`, страницы `403.ejs`, `404.ejs`,
`error.ejs`. Коды: 400 — некорректные данные, 401 — не выполнен вход, 403 — недостаточно
прав, 404 — нет маршрута или записи, 409 — нарушение уникальности, 500 — внутренняя
ошибка. Пользователь видит только понятное сообщение: stack trace, SQL и содержимое `.env`
в ответ никогда не попадают, они пишутся только в логи сервера.

**Логирование.** Morgan в `config/logger.js` пишет строки вида
`GET /venues | 200 | 12 ms` одновременно в терминал и в `logs/access.log`.

**Статистика.** `GET /statistics` защищён middleware `isAuthenticated`. Страница показывает:
общее число площадок, общее число броней (и отдельно активные/отменённые), распределение
площадок по видам спорта, распределение броней по статусам, среднюю цену за час
(`AVG`) и самую дорогую площадку (`ORDER BY pricePerHour DESC`). Все показатели считаются
запросами PostgreSQL.

**Socket.IO.** В `app.js` создаётся `io`, в контроллере создания площадки вызывается
`req.app.get('io').emit('venue:created', ...)`. В payload передаются название площадки,
имя администратора, время создания и `id`. Клиентский `public/js/socket.js` показывает
toast с кнопкой закрытия; уведомление также исчезает само через 9 секунд.

**Интерфейс.** Общий стиль лежит в `public/css/style.css`: header с навигацией, полоса
текущего пользователя, footer, карточки, таблицы, формы, бейджи статусов, сообщения
об ошибках и контейнер уведомлений. Пункты меню и кнопки зависят от роли, но главная
защита всегда выполняется на сервере, а не скрытием кнопок в EJS.

## 8. Установка и запуск

### Вариант A — контейнеры 

```bash
just setup          # создаст .env из .env.example, если файла ещё нет
just up             # соберёт образ и поднимет app + PostgreSQL
just seed-docker    # заполнит БД тестовыми данными
```

Открыть: <http://localhost:3000>. Порт БД на хосте — `5433` (внутри сети Compose БД
доступна как `db:5432`); если порт занят, задайте `DB_PORT_HOST=5434` в `.env` перед `just up`.

Полезные команды:

```bash
just logs           # логи приложения
just access-log     # строки Morgan из logs/access.log
just psql           # psql внутри контейнера БД
just test           # интеграционные проверки HTTP
just test-socket    # проверка Socket.IO с двумя клиентами
just check          # обе проверки сразу
just down           # остановить контейнеры
just reset          # удалить контейнеры и том с данными
```

Команды `just test` и `just test-socket` выполняются внутри контейнера `app`, поэтому
установка `node_modules` на хосте для них не нужна. Перед передачей я удалил `node_modules`
и `.env`: `just up` создаст `.env` из `.env.example` автоматически.

### Вариант B — локальный запуск без контейнеров

```bash
createdb -U postgres travel_db       # или другой способ создать БД
npm install
cp .env.example .env                 # затем заполните свои значения
npm run seed                         # тестовые данные (опционально)
node app.js                          # или npm start
```

## 9. Создание базы данных и конфигурация

В контейнерном варианте база `travel_db` создаётся автоматически переменной
`POSTGRES_DB` из `docker-compose.yml`; данные хранятся в именованном томе `pgdata`.
При локальном запуске базу нужно создать вручную, например `createdb -U postgres travel_db`.
Таблицы `Users`, `Venues`, `Bookings` создаёт Sequelize при старте, таблицу `Sessions` —
хранилище сессий.

Файл `.env` в проект **не входит** (он в `.gitignore`). Ниже безопасный пример:

```dotenv
DB_HOST=localhost
DB_PORT=5432
DB_NAME=travel_db
DB_USER=postgres
DB_PASSWORD=change_me
SESSION_SECRET=change_me_to_a_long_random_string
PORT=3000

ADMIN_EMAIL=admin@easysport.local
ADMIN_PASSWORD=Admin123
```

Пароль БД и секрет сессии читаются только из окружения: в коде нет ни одного значения
по умолчанию для этих секретов — если их не задать, приложение не запустится.
